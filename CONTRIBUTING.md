# Contributing

Start with the README and docs/DEMO.md. Use an isolated checkout and the documented runtime versions. Do not connect tests to production data or services.

Keep each change focused on one behavior. Explain the problem and resulting behavior in the commit or pull request, include the relevant verification result, and preserve recovery history. Add regression coverage when changing behavior or extracting modules; documentation-only edits need valid links and truthful examples.

Use authored fixtures for offline checks. Distinguish fixture results from live-provider evaluations, including their cost and limitations when applicable. Do not submit credentials, personal conversations, customer data, downloaded runtimes, or generated caches.

Preserve upstream notices and the source-review policy in LICENSE.md. Changes involving paid providers, user assets, or active infrastructure need an explicitly agreed scope.
